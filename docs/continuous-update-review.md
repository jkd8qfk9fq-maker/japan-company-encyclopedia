## 1. 新規・訂正・変更の検知 — △

- 〇 新規有報（120）と訂正有報（130）は、日次索引と `parentDocID` で検知できる。訂正は会社が登録済みかどうかに関係なく全件を見る設計で、原本が古くても見落とさない。
- **△ R1（書類の変更の検知が抜けている）。** 要件の「提出済み書類の変更」は、`docInfoEditStatus` の変化として索引に現れる（上の実例）。提案書の台帳は「初めて見た書類だけ job を作る」ため、**日をまたいで再掲された書類の更新を拾わない**。直す: `edinet_filings` に `edit_status`・`last_seen_day`・`row_hash` を持ち、変化したら `doc-edited` の job（`unique(doc_id, kind, row_hash)`）を作る。日ごとの `doc_count` は、同じ docID の再掲を含むので書類数とは別物と明記する。
- **△ R2（取下げの無視）。** 120/130 で `withdrawalStatus ≠ 0` の行は「取下げ」として記録し、最新の有報の候補にしない。今は該当が0件だが、規則は先に入れておく（テストあり）。
- **△ R3（確定後の再確認）。** 確定済みの日を永久に信じない。毎夜、直近7日分を取り直して `row_hash` を比べ、変化があれば再処理する（標本14日は変化0件だが、変化の種類は書類情報の修正が最もありうる）。

## 2. 日次索引の確定判定と台帳の欠落・重複 — △

- 〇 `processDateTime` が当日より後、という確定判定は、実データで裏付けがある（今回見つけた2026-10-02の144件→244件の不具合を、この規則が検出した）。ただしこれは**観測から導いた規則で、EDINET の仕様ではない。** R3 の再確認と、確定判定を1か所（`indexProblem`）に集める設計がその保険になる。
- **✕→△ R4（監視位置が進まなくなる）。** 「全書類が job の判断まで記録済み」を進める条件にするなら、**全書類に判断（job を作る／対象外とその理由）が付く規則**が要る。決まっていないと、判断のない書類が1件あるだけで位置が止まる。直す: 書類ごとに `disposition`（`job` / `ignored:<理由>`）を必ず持たせる。無視してよい書類種別を一覧にして提案書に載せる。
- **△ R5（同時実行）。** cron が重なる（前回が長引く）と、同じ日を2つの実行が更新する。台帳の一意制約で重複は防げるが、`partial`／`final` の上書き競合が起きうる。直す: 実行全体に `pg_try_advisory_lock`（取れなければ即終了）、日の更新は `where status <> 'final'`。
- **△ R6（初回の投入）。** 起点から730日を最初の cron で取り直すと関数の実行時間を超える。直す: 手元のキャッシュ（730日分が確定済み）から台帳に**種付けする**手順（`seed`）を最初の段階に入れる。
- **△ R7（永久に取れない日）。** 取得に失敗し続ける日があると位置が進まない。**進めない（見落とし防止）を維持し、人に知らせる**のが安全。「隔離して先へ進む」は見落としを隠すので採らない（意思決定一覧に入れる）。
- 〇 日ごとの更新を1トランザクション（書類・job・日の状態、`final` は最後）にする設計は正しい。

## 3. 中断・再実行・API／DB 障害からの復旧 — △

- 〇 A（検知）: EDINET 障害の日は `failed` のまま残り、次回に再走査。DB 障害ではその回が失敗して何も記録されず、次回は台帳（＝真実）から再計算するので、**「前回どこまで」を別に持たない**この設計は安全。DB が落ちているときの health は 503（不明＝異常）にする。
- **△ R8（B の再実行は登録を重ねられない）。** B の副作用は DB の外（ファイル、改訂記録）。`finalize.mjs` の改訂記録の id は `<日付>-company-<id>-(described|initial)` で、**同じ日に既にあれば失敗する**（安全だが、中断後に素直に再実行すると失敗）。直す: B の実行器は、状態が `running` で中断された会社には必ず先に `recover-registration.mjs --dry-run` を試し、条件を満たすときだけ復旧する。**判断表**（未着手→advance／running で中断→recover／completed→何もしない）を設計に入れる。
- **△ R9（無駄な再登録）。** 「新しい情報がない会社を再登録しない」は、job の実行前に**登録済みの出典の docID と検知した docID が違うことを確かめる**ゲートが要る（今の `finalize` は呼ばれれば必ず改訂記録を作る）。

## 4. 重複登録・誤った改訂記録の防止 — △

- 〇 `unique(doc_id, kind, …)` と、B だけが改訂記録を書く構成は、重複の防止になる。訂正の適用は `-N` の連番で衝突を避ける（`apply-amendment.mjs`）。
- △ 改訂記録を書く経路が複数ある（`finalize`: 衝突で失敗／`apply-amendment`: 連番）。自動化では**「job 1件につき改訂記録は最大1件」**を、job の `result_ref` に記録して守る。

- △ R12（状態の持ち主）。DB の job（要求）と、手元の `pipeline/state`（処理の実態）の2か所に状態ができる。**処理の実態は手元が正、DB の job は要求と結果の写し**と決め、B が結果を書き戻す経路（トークンつき API）を設計に入れる。

## 6. 検知と公開の分離 — 〇（1点を訂正）

- 〇 A は DB にしか書かない。`src/data` を書くのは B（手元の finalize）だけで、公開は人の commit。**job の `done` は「公開した」の意味ではない**と、状態の語彙で分けておく（`proposed` を追加）。
- **△ R13（提案書の記述の誤り）。** 「検証に失敗したものは staging にも出さず」は不正確。`finalize.mjs` は**先に staging を書いてから**検証する（staging は git 管理外で、`src/data` には入らない）。正しくは「検証に失敗したものは `src/data` に入らず、job は needs-review」。提案書を直した。
- 注意: B が手元で動くと、**作業ツリーの `src/data` が自動で書き換わる**（commit はしない）。公開の分離は「B は commit しない」で守られる。B を人の見ていない環境で動かすなら、作業ツリーを分ける（ブランチか別チェックアウト）。

## 7. 認証情報・アクセス制御・ログ・通知・運用監視 — △

- 〇 管理画面は既存のセッション（HMAC のクッキー、`requireAdmin`、強制動的）をそのまま使える。読み取り専用のページなので、本番の「コンテンツは書かない」と矛盾しない。
- **△ R14（cron の認証）。** `Authorization: Bearer ${CRON_SECRET}` を**定数時間比較**し、未設定なら**閉じる**（管理画面の設定と同じ流儀）。メソッドは GET のみ。`/admin` のクッキーとは別系統（クッキーの path が `/admin`）。
- **△ R15（health の情報量）。** 公開の `/api/health/edinet-watch` は、`ok`／503 とコードだけ。件数・会社名・時刻の詳細は出さない（管理画面に置く）。
- **△ R16（API キーの漏えい経路）。** EDINET のキーは**URL のクエリ**（`Subscription-Key=`）で送る。URL やエラーの生の出力をログに出すと漏れる。現行の `fetchWithRetry` は `HTTP <状態>` しか投げないが、**本番では URL・エラーの原文をログに出さない**規則を決める。キーは Vercel の Sensitive 環境変数にし、更新の手順（ローテーション）を決める。EDINET の API の**自動実行での利用条件**は、確認していない（意思決定一覧）。
- **△ R17（権限の分離）。** 監視のテーブルを、読者の報告（`content_reports`、`submitter_hash`）と同じ DB・同じ接続で書くのは、権限が広い。別のロール（または `WATCH_DATABASE_URL`）にする。B が手元から DB を直接読み書きするのは、資格情報を手元に置くことになる。**トークンつきの API（`WATCH_API_TOKEN`）経由**を推奨する。
- **△ R18（通知）。** 今のコードに通知の仕組みは無い。「監視が止まった」を**止まる側自身に通知させない**（デッドマンスイッチ）: 外部の稼働監視が health を定期的に見に行く形にする。Vercel 側の失敗通知は、仕様を確認していない。
- △ 既存の弱点: 管理画面のログイン試行の制限はメモリ内（サーバーレスでは効きが弱い。JCE-015 に記載済み）。監視ページは同じ認証の後ろに置く。

## 8. 既存の不変条件・決定・テストとの矛盾 — △

- 〇 不変条件1（捏造しない）: 上場状況は推測で確定しない設計。JPX の差分も `needs-review`。不変条件8（既定は Server Component）: 監視ページは Server Component、cron はルートハンドラで、`"use client"` は不要。命名（kebab-case の経路、snake_case の列）も既存の規則どおり。
- **△ R19（JCE-016 との関係）。** JCE-016 は「本番はコンテンツを書かない」「**本番から GitHub API／PR は作らない（まだ）**」「**費用ゼロ・運用が単純**」を決めている。提案の PR 経路は、この決定の変更（新しい決定の記録が要る）。有料の Postgres／Vercel Pro も「費用ゼロ」と衝突しうる。**この段階の実装（検知と記録まで）は JCE-016 に収まる**が、PR 経路と有料プランは変更になる。
- **△ R20（テスト）。** 必須の8項目は、時計（`now`）と取得（`fetch`）を差し込む設計にすれば既存の流儀（vitest・一時ディレクトリ）で書ける。**ただし Postgres の SQL そのものをテストする手段が今は無い**（`pg` の実接続のテストが無い）。リポジトリ共通の契約テスト（ファイル実装と Postgres 実装に同じテスト）と、Postgres を使う検証の置き場所（手元の Docker／CI）を決める。Postgres 実装をテストせずに本番に出さない。
- 〇 `tests/data-integrity` は、この機能がコンテンツを書かない限り影響を受けない。

## 結論

提案の骨格（3層、台帳から導く監視位置、公開を変えない）は妥当。**実装に進む前に直すこと**は次の4点:

1. 書類の変更（R1）・取下げ（R2）・確定後の再確認（R3）を台帳に入れる。
2. 全書類に判断（`disposition`）を付ける規則（R4）と、同時実行の抑止（R5）、手元のキャッシュからの種付け（R6）。
3. **登録済みの会社の更新の実行器が無い（R10）**ことを提案書に明記し、段階を分ける。B の再実行の判断表（R8）と、再登録のゲート（R9）を入れる。
4. 認証・ログ・権限の規則（R14〜R17）を決め、Postgres のテスト手段（R20）を用意する。

別紙の意思決定が済むまで、本番の実装には入らない。
